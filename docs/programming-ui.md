# Authenticated programming controls

The admin sidebar exposes station-scoped Categories, Rotations, Clocks, and Schedule. An active global administrator may submit these forms; every POST requires the session CSRF token. All mutations use the programming services shared with root CLI, which remains the recovery path. Forms save atomically and record an audit event in `/admin/audit`. Public programming APIs remain read-only.

Create a category with a stable slug; edit its name and description, and assign or remove up to 100 visible station tracks at once. Search narrows the membership chooser to 100 results. The media detail page also supports category membership. Disabling a category referenced by enabled programming is blocked. Disabled or empty categories may leave a rotation with no playable candidate; review the slot and preview before activation.

Create a rotation, add category slots, and use keyboard-accessible up/down buttons to reorder. A rotation is not activated when created. The validation panel reports structural errors; preview simulates 10, 20, or 50 decisions without changing history, queue, or cursor. To use a rotation as the station fallback, type its slug to confirm activation. Activation does not restart the worker or playout. The currently playing item and queued requests may finish; future decisions use the committed sequence. Empty final enabled slots cannot be removed while the parent remains enabled.

Create a clock with `CATEGORY` or `ROTATION` slots only. The target must belong to the same station and be enabled; unsupported types fail. Reorder and preview as for rotations. Clocks are reusable; creating one does not schedule it. Disabling a default or scheduled clock is blocked. The worker normalizes its durable cursor against the new slot count after an edit.

The Schedule page shows seven day cards in the station timezone. Add, edit, or remove a recurring weekday/local-time assignment; duplicate station/day/time keys fail. Removal asks for the assignment ID. The preview shows clock transitions for a selected local date over 24 hours or seven days and does not change runtime state. The station timezone form requires the current timezone as confirmation because the same weekly wall times then map to different UTC instants. DST interpretation is documented in [scheduling](scheduling.md).

Changes become visible to the automation worker through PostgreSQL without restarting Liquidsoap, Icecast, or the worker. A current track continues; already queued requests can delay the first new-rule start. `/admin/audit` records programming mutations; recent confirmed playback history exposes clock, slot, rotation, category, and relaxation context. No cart, hard-time, skip, live-assist, or station service controls are offered in the browser.
