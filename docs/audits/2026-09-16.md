# Freo audit — 16 September 2026

See the [subsequent player and audio-engine fixes](2026-09-16-followup.md) for updated results. The findings and failures below describe the original audit run.

Reviewed checkout: `a5e9788`. This is a source, test, deployment, and usability-readiness audit, not a guarantee that every workflow or vulnerability has been found. The audit used isolated databases/media for destructive workflow tests and read-only production checks. During the audit, the owner reported a Safari pause/resume failure; the subsequent player fix is documented below. Production station data was not changed.

## Assessment

Freo has a substantial foundation for a first public project: a functioning public stream, separate web/ingest/automation/playout processes, database migrations, station ownership checks, CSRF protection, audited mutations, and extensive browser and audio tests. The main weakness is release engineering: the working development server has capabilities that a fresh download does not reliably reproduce. Stabilize installation, upgrades, account security, and recovery before adding more broadcast features.

## Prioritized findings

### 1. High: login throttling can be reset by deleting cookies

`app/routes/web.py:207–220` stores both the failure count and lockout in the signed client session. Reproduced in an isolated database: five wrong passwords returned 401; the sixth returned 429; a new client immediately returned 401 and performed another password check. No server-side or checked-in Nginx login limiter compensates for this.

Use shared server-side attempt accounting across Gunicorn workers, with account and trusted-client-IP limits, expiration, and tests that change cookies and workers. Keep errors generic. An IP-only permanent account lock would introduce a denial-of-service problem; use bounded backoff.

### 2. High: ordinary out-of-tree installation omits a station-provisioning dependency

`scripts/provision.sh:121–129` copies two Python helpers into the installation's scripts directory, but never installs `scripts/media-web-access.sh`. `app/services/station_lifecycle.py:50` later runs that exact helper from the installed application root. Installing from an extracted release or checkout outside `/opt/freo` therefore leaves station creation dependent on a missing file. Existing in-place deployments conceal the omission. The validator does not check this dependency.

Package a complete explicit release manifest and validate it. Acceptance must create a station after installing from a separate source directory, then verify provisioning completion and streamed audio. Copy the operator validation/upgrade tools and optional-feature assets too, or document clearly where they remain available.

### 3. High: documented HTTP setup cannot support normal production login

`scripts/provision.sh` generates `FLASK_ENV=production` and an HTTP URL; HTTPS is optional. `app/__init__.py:114–115` always marks production session cookies Secure. On a normal remote HTTP origin, the browser cannot send the required session cookie, affecting login CSRF and authentication. Localhost-based tests do not validate this deployment path.

Make verified HTTPS part of the production setup flow. Provide an explicitly local development/demo path separately. Test installation using an actual non-localhost origin. Flask documents that Secure cookies are limited to HTTPS: [Flask security guidance](https://flask.palletsprojects.com/en/stable/web-security/).

### 4. Medium: password changes do not revoke authenticated sessions

`app/admin_cli.py` changes the password hash, but `app/services/admin_auth.py:14–17` checks only the user ID and active flag. Reproduced: log in, replace the user's password hash, then request `/admin` with the old session; it still returns 200. The one-hour session lifetime is not a reliable emergency revocation mechanism, especially with sliding session refresh.

Add a per-user session version and compare it on every authenticated request. Increment it on password changes, account recovery, and explicit logout-all actions. Test copied old cookies as well as the current browser session.

### 5. Medium: upgrades leave workers executing old code

`scripts/provision.sh:142` restarts the web service. Lines 156–157 only use `enable --now` for automation and ingest; already-running services remain running with previously imported Python code. Database migrations and the web application can therefore advance while long-lived workers do not.

Design an upgrade sequence with a backup/preflight, compatibility checks, controlled worker restarts, and post-upgrade version/heartbeat checks. Treat station-engine configuration changes as a separate broadcast maintenance operation. Copying files over a running application is not an atomic release or rollback strategy.

### 6. Medium: dependency advisories require updates and applicability review

A fresh `pip-audit` scan of the installed environment reported 50 records across two packages. The feed duplicates entries: there are **25 unique advisory IDs**, comprising 24 for `aiohttp==3.13.3` and one for `pytest==8.4.2`. This is not 50 proven remotely exploitable flaws in Freo. `aiohttp` belongs to the optional live microphone stack, whose HTTP listener is loopback-only; many advisories concern features not used here. `pytest` is development tooling.

The scan reports fixed versions through aiohttp 3.14.3 and pytest 9.0.3. Validate supported patched versions in a separate environment, rerun microphone/browser/audio tests, then update the pins. Add dependency auditing and update automation to CI. The requirements pin direct dependencies but do not lock/hash the full transitive dependency set.

Scanner: [pip-audit](https://github.com/pypa/pip-audit). One upstream server-parser advisory: [aiohttp upstream advisory](https://github.com/aio-libs/aiohttp/security/advisories/GHSA-mfx4-hv73-q22v). Exact advisory applicability needs review; do not equate scanner counts with severity.

### 7. Medium: listener network throttling sees the reverse proxy's address

`app/routes/player_experience.py:210` derives its network limiter from `request.remote_addr`. The deployed topology proxies to Gunicorn over loopback, and the application has no client-IP proxy middleware. The checked-in Nginx forwarding header does not by itself rewrite Flask's remote address. Consequently, the intended per-network quota can become a shared quota for all listeners to a station. This is a source/topology finding, not a production load test.

Trust exactly the configured proxy hop and overwrite/validate forwarding headers at the edge. Test multiple simulated external clients and spoofed headers. Flask explicitly warns that incorrect proxy trust is a security issue: [Flask proxy configuration](https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/).

## Security strengths and remaining boundaries

- Passwords use scrypt; bootstrap prompts avoid command-line passwords. There is no default admin account.
- Admin routes use centralized authentication and CSRF checks. Station-scoped lookups and concurrency tests cover important cross-station and lost-update cases.
- Production cookies are HttpOnly/SameSite/Secure; HTML has CSP and frame restrictions; admin pages prohibit caching.
- Web and radio processes run under separate accounts with systemd hardening; backend database, web, Icecast, and microphone ports were observed on loopback.
- Media probing has timeouts, format checks, private storage, and controlled paths. Root station operations use validated slugs and fixed command argument lists.
- A limited high-confidence tracked-file credential-pattern scan found no matches. Selected sensitive filenames were absent from Git history. This was not an exhaustive historical secret scan.
- Bandit found 28 low and five medium signals, no high signals. The medium signals concern intentional directory permissions, a fixed loopback URL, and XML generated from controlled templates/validated values. They are review signals, not five confirmed vulnerabilities.
- All active admins currently have global management/playout access. Do not present this as station-isolated multi-tenant access control.
- The host also listens on port 631 on all IPv4/IPv6 interfaces. Verify whether that service is needed and how the firewall restricts it; external reachability was not tested.

## Make installation easy

Choose one supported production route first: Ubuntu 24.04, a domain, and automatic HTTPS. Keep the existing systemd architecture until its fresh-install and upgrade paths are proven.

1. Publish versioned GitHub release archives with checksums and a complete runtime manifest. Both Git clone and direct-download users should end up running the same installer.
2. Run preflight before changing the machine: OS, architecture, RAM/disk, existing services/ports, DNS, permissions, required downloads, and database state. Explain failures in actionable language.
3. Ask for domain and certificate email, obtain HTTPS, generate secrets, apply migrations, and prompt privately to create the first admin. Finish with a working login URL and a health summary.
4. Add a first-run wizard: create station → upload a legal test track → choose timezone → configure default programming → start broadcast → listen. Show provisioning progress, failures, and retry actions.
5. Offer documented `check`, `backup`, `restore`, and `upgrade` operations, including tested recovery from failed migrations and interrupted installs. Make backups include database, media, configuration, and secrets with appropriate protection.
6. Run release acceptance on a disposable clean VM: install from archive outside `/opt/freo`, log in over HTTPS, create two stations, upload/play audio, change settings, delete one while the other keeps playing, reboot, rerun installer, upgrade, restore, and repeat checks.
7. Only then advertise a one-command installation. A Docker demo could reduce evaluation friction later, but production containers introduce additional audio, WebRTC, persistence, and upgrade work.

## Public-project and product improvements

- Replace the README's phase-by-phase opening with purpose, screenshot, working features, supported install, quick start, and explicit limitations. Correct stale claims that station lifecycle is CLI-only and that microphone switching is unsupported when the optional feature is enabled.
- Select a license deliberately; add `LICENSE`, a root security reporting policy, release notes, and issue templates. No license choice was made on the owner's behalf.
- Add CI for unit/route tests, portable Chromium browser tests, PostgreSQL migrations/concurrency, dependency scanning, and isolated engine tests. Browser fixtures currently hardcode `/usr/bin/chromium-browser` and `/usr/bin/chromedriver`; make these configurable and document system dependencies.
- Most valuable additions: guided setup, backup/restore with a restore drill, disk/queue/worker/silence alerts, an operator health screen with useful failure explanations, and explicit station-level roles if multiple operators need separation.
- Add keyboard/screen-reader checks and real Safari/Firefox/mobile playback tests. Existing viewport tests do not establish cross-browser accessibility.
- Refactor the largest model/worker/booth modules gradually as behavior is covered. Dense one-line Python and long JavaScript handlers make a public contribution harder to review. Avoid a broad rewrite during stabilization.

### Audio acceptance remains incomplete

The explicit engine run finished with **17 passed, 2 failed** in 728 seconds. Passing cases include recorded crossfades, Auto skip, cart exclusivity/programming refresh, two-station stream lifecycle isolation, and real microphone fade/return/disconnect.

- `test_actual_worker_load_play_pause_repeat_clear_and_mode` failed during cleanup/control of its four-second track: the deck was already empty when CLEAR was requested. A targeted rerun failed again, this time because the deck changed before the worker applied command 11. The application deliberately rejects stale commands; these observations do not establish that accepting the command would be correct. Use longer fixtures and synchronize against observed engine states, then test end-of-track operator races explicitly. Do not weaken the stale-command guard just to make this pass.
- `test_soft_insert_preserves_current_song_and_all_future_requests` initially observed request IDs `[1, 3, 2]` where it expected `[3, 1, 2]` immediately after insertion. It passed on the targeted rerun. This is unresolved intermittent queue-order/timing behavior. Review `program_queue()` in the Liquidsoap template, including in-flight prefetch during queue replacement, and prove actual playback ordering across repeated boundary tests.

The targeted rerun was **1 passed, 1 failed**. Neither a single retry pass nor an apparently timing-sensitive failure is sufficient to claim all broadcast controls are reliable. This is a release acceptance gap that deserves attention before broad production promotion.

## Player fix requested during the audit

The owner reported that pausing and resuming the public player leaves Safari silent. The old implementation called `play()` on the existing paused resource and reloaded only on an explicit error/retry. A new browser regression failed against that implementation because resume produced no new stream request.

Changed `app/static/player.js` to close/release the paused resource and open a fresh live stream on every play. Playback starts within the click/media-session handler, preserving the user-gesture requirement. Attempt generations prevent rejected old play promises from overriding newer taps; delayed pause events no longer cancel a new connection. A 15-second connection/buffering watchdog uses the existing bounded retry policy. Buffered playback is not interrupted merely because a network `stalled` event occurs while audio remains ready. Updated the template's script version to invalidate old asset references.

Validation:

- Original regression: failed because resume did not issue a new stream request.
- Updated player browser suite: **4 passed**. Covers existing listening/calendar/feedback/ads workflows plus repeated pause/resume on desktop and 390×844 layouts, fresh HTTP requests, advancing playback time, rapid taps, a hung play promise, reconnect, and a stale promise rejection.
- JavaScript syntax and Git whitespace checks passed.
- Gracefully reloaded only the web service workers; public HTML serves the new `20260916-resume` asset version, and readiness returns 200.
- Against the real public HTTPS MP3 stream, Chromium passed initial play, pause, fresh connection on resume, and advancing playback on both desktop and phone-sized layouts.
- Native Safari/iPhone testing is not available in this Linux environment. The owner was asked to refresh Safari and verify the fix on the affected device; Chromium viewport checks are not a substitute for that result.

References for media reset and aborted play promises: [MDN media load](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/load) and [MDN media play](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play).
