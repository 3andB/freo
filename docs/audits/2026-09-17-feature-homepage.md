# Freo feature audit for the project homepage

Reviewed 17 September 2026. Companion: [homepage redesign plan](../homepage-redesign-plan.md).

## Scope and evidence

This review inventories the current project's public experience, authenticated workspaces, audio and scheduling services, supporting infrastructure, documentation, and relevant tests. It informs the homepage's content and design. It is not a new exhaustive security assessment, production load test, or fresh-server installation certification.

The checkout contains existing modified and untracked statistics/deployment work. That work is included in the inventory because the application registers it and the screens/services exist. It must be preserved during homepage implementation. The statistics guide records deployment on September 17; that deployment was not independently repeated for this audit.

Source, templates, and newer rollout records take precedence over older phase-based descriptions. Existing product screenshots and fresh isolated Chromium screenshots were inspected. No production database or broadcast configuration was changed.

## Product assessment

Freo's strongest story is the connection between music preparation, flexible programming, hands-on broadcasting, the listener player, and measured station performance. Its identity combines an expressive record-inspired interface with substantial operational tools. The homepage currently communicates only a small fraction of that story.

The main navigation now includes Music, Categories, Tags, Playlists, Imaging, Schedule with Calendar/Shows/Blocks/Simple/Events, Statistics, History, station/player settings, feedback, copyright reports, and installation management. The DJ Booth exposes Auto, DJ Booth, and Live Mic views. Traffic planning and event sequences also exist, with less prominence in current navigation.

## Findings that affect the homepage

1. **Coverage is far too narrow.** The current page has three introductory cards, two product images, a station list and setup links. It omits playlists as a first-class workflow, the current scheduler, Live Mic, statistics, most player features, multi-channel sharing and the technical architecture.
2. **The two embedded product images are obsolete.** `product-dj.png` and `product-schedule.png` show the previous dark appearance/navigation. The former includes Sound Room; the latter shows the superseded calendar. Switching the homepage to Day leaves both images dark.
3. **The headline does not identify the product category.** A new visitor can read the first screen without learning that Freo is self-hosted internet radio automation and station management. Add that description prominently.
4. **The primary action assumes ownership.** “Open your studio” leads visitors to authenticated administration. Make the primary discovery action a product tour, with setup documentation as the next conversion. Keep sign-in available for existing operators.
5. **Current screenshots are unreadable at phone width.** Desktop admin chrome, the full sidebar and tiny buttons overwhelm the useful content. Use authentic detail crops and native mobile captures, plus enlargement.
6. **Mobile navigation consumes too much space.** The fresh authenticated phone screenshot places branding, theme, monitor, sign-out and wrapped navigation above the hero. Use a compact public header with an accessible menu and preserve active monitoring for signed-in users.
7. **Some documentation conflicts with current code.** Sound Room is a legacy redirect; the scheduler now offers Calendar/Blocks/Simple plus Shows; Live Mic exists; newer imports can auto-enable after analysis; overlay carts exist. Resolve copy against implementation and newer rollout records.
8. **Two meanings of “Blocks” need clear language.** Use “24-hour Blocks” for day formats and “event sequences / stopsets” for ordered timed content. Likewise distinguish booth Auto/DJ/Live Mic views from Calendar/Blocks/Simple scheduling modes.
9. **Analytics needs accurate definitions.** Show compelling maps/charts with labeled demo data, but do not turn test fixtures into customer/reach/uptime claims or present sampled connections as people.
10. **The homepage station query differs from the directory.** `web.homepage()` excludes disabled/deleted rows but does not exclude `pending_delete`/`delete_failed` lifecycle states as `web.stations()` does. If retaining homepage station cards, align eligibility and test it. A simple directory link avoids duplicating this query.
11. **Traffic is difficult to discover.** Its routes and workflow exist, but neither the sidebar nor current scheduling tabs links to it. A homepage should document it accurately; improving admin navigation is a separate product change.
12. **The public-project status needs honest framing.** No checked-in license was found. README/installation docs still state fresh-VM installation is unverified. Promote self-hosting and inspectable source, with setup/status links; avoid “open source,” guaranteed production readiness and effortless one-command installation until supported.

## Operational context carried forward

The [September 16 audit](2026-09-16.md) and [follow-up](2026-09-16-followup.md) should inform public claims. The follow-up records fixes and passing isolated checks for event insertion and deck-control timing. Do not repeat those as unresolved failures. Native iPhone confirmation, WAN microphone/device acceptance, fresh-install recovery and production-scale behavior remain separate acceptance work.

Current source inspection still shows cookie-session login throttling, no password/session-version revocation check, the missing out-of-tree copy of `media-web-access.sh`, optional HTTP provisioning alongside Secure production cookies, and `enable --now` rather than explicit restart of existing automation/ingest workers. The feedback limiter still derives its network key from `request.remote_addr`. These are relevant release-engineering/security backlog items, not homepage implementation tasks. This review did not refresh vulnerability feeds or run a new dependency advisory scan.

The positive architecture claim is concrete: web requests record validated intent, the automation worker controls private engine sockets, and per-station Liquidsoap processes deliver audio through Icecast/Nginx. Explain that separation rather than making broad claims such as “enterprise-grade security.”
