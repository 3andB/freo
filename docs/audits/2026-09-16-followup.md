# Player and audio-engine follow-up — 16 September 2026

This follows the initial [audit](2026-09-16.md). The owner confirmed that the first player revision still required a page refresh in Safari, and requested fixes for both audio-engine findings.

## Player revision 2

Manual play now creates a new audio element inside the user's gesture and opens a distinct stream URL. This releases the old native media resource and avoids reusing the same cached stream identity. Volume and mute are retained. The previous element's event listeners are aborted, so its late events cannot change the current playback state. Automatic reconnects retain the current element's playback permission while changing the URL. The redundant explicit `load()` immediately after assigning `src` was removed.

The script version is `20260916-safari-resume-2`. The web workers were gracefully reloaded so a page refresh loads that version. Four player browser tests passed, and the final focused regression passed again after correcting its consecutive-URL assertion. Coverage includes an unrecoverable old media element, repeated pause/resume, fresh URLs and requests, advancing playback, volume/mute preservation, rapid taps, stale events/promises, and recovery from a hung play request.

The public HTTPS MP3 stream also passed repeated playback tests in Chromium desktop/phone layouts and Playwright WebKit desktop/iPhone emulation. WebKit ran with temporary downloaded browser libraries; no system packages were installed for these checks. Linux WebKit does not reproduce the iPhone's native media stack: even the first revision passed that environment. The owner must still confirm the second revision on the affected physical device; do not describe native Safari as conclusively fixed without that confirmation.

## Event insertion order

The old program source maintained both a waiting list and a background prefetch queue. A request could leave the waiting list for resolution while insertion reconstructed the future queue; the background fetch could then append that request ahead of the intended event. The source now holds one resolved future queue. Approved local media is resolved on insertion, with no independent prefetch callback moving requests between lists.

Real-engine tests with two and six future songs assert both the immediate queue order and actual confirmed playback: current song finishes, inserted event plays, then every queued song plays in its original order. Auto skip, programming refresh, cart exclusivity, crossfades, station lifecycle isolation, and microphone fallback also pass with the changed template.

## Deck-control test timing

The stale-command protection was correct and remains unchanged. The original four-second test track could end while the test was still issuing controls. In addition, engine current-track metadata and the durable playback-start event can be observed in different worker cycles.

The acceptance test now uses a longer generated track, waits for both the repeated track and its confirmed start, and pauses it before exercising explicit cleanup. Unit coverage separately verifies that CLEAR is rejected without issuing an engine command when the expected song has either changed or ended. No production permission or stale-target check was relaxed.
